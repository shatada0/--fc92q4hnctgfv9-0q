# ЛР8. Основы нагрузочного тестирования с k6

Объект тестирования: API калькулятора учебного стенда, `GET /api/calc?a=2&b=3&op=add` → `{"result": 5}`. Код: `app.py` (маршрут `api_calc`, функция `calculate`). Стенд запущен встроенным сервером Flask без режима отладки (`app.run(port=5000)`).

## 1. Цели теста (ручное задание)

| Что проверяем | Вопрос | Критерий (порог k6) |
|---------------|--------|---------------------|
| Время ответа | Укладывается ли API в норму при 10 и 50 одновременных пользователях? | 95% ответов быстрее 300 мс: `http_req_duration: p(95)<300` |
| Надёжность | Не появляются ли ошибки под нагрузкой? | ошибок меньше 1%: `http_req_failed: rate<0.01` |
| Корректность | Под нагрузкой API отвечает правильно, а не просто быстро? | больше 99% успешных проверок: `checks: rate>0.99` |
| Пропускная способность | Сколько запросов в секунду выдерживает стенд? | без порога, измеряем `http_reqs` (RPS) в стресс-прогоне без пауз |
| Устойчивость | Что ломается первым при перегрузке? | анализ ошибок стресс-прогона |

Пороги записаны в `options.thresholds` скрипта: если цель не достигнута, k6 помечает порог ✗ и завершается с ненулевым кодом.

## 2. Установка

```
winget install k6 --source winget
k6 version   →   k6.exe v2.2.0
```

## 3. Скрипт

Файл `load/get.js`: каждый виртуальный пользователь (VU) в цикле отправляет GET-запрос, проверяет статус 200 и значение `result == 5` (`check`), затем делает паузу 1 с (`sleep`), как реальный пользователь между действиями. Пауза задаётся переменной `SLEEP`, адрес стенда — `BASE_URL`.

## 4. Прогоны

```
k6 run --vus 10 --duration 30s --summary-export docs/lab8/summary_10vu_30s.json load/get.js
k6 run --vus 50 --duration 10s --summary-export docs/lab8/summary_50vu_10s.json load/get.js
k6 run -e SLEEP=0 --vus 50 --duration 10s --summary-export docs/lab8/summary_50vu_10s_nosleep.json load/get.js
```

Третий прогон дополнительный: стресс-тест без пауз, каждый VU шлёт запросы так быстро, как может.

Полный вывод: `run_*.txt`, итоговые метрики в JSON: `summary_*.json`. Дата: 21.10.2026, Windows 11, стенд и k6 на одном компьютере.

## 5. Анализ

- **Количество запросов.** С паузой 1 с каждый VU делает примерно один запрос в секунду, поэтому RPS почти равен числу VU (9,9 и 49,2). Нагрузка в этих прогонах ограничена сценарием, а не сервером.
- **Время ответа.** При росте нагрузки с 10 до 50 VU p(95) вырос с 26 до 50 мс: запросы чаще приходят одновременно и ждут в очереди. Это в 6 раз меньше порога 300 мс. Цель по времени ответа достигнута.
- **Ошибки.** В обоих основных прогонах 0 ошибок и 100% правильных ответов.
- **Пропускная способность.** Без пауз стенд обработал около 1150 запросов в секунду при p(95) 50 мс, время ответа почти не выросло по сравнению с 50 VU с паузами.
- **Устойчивость.** В стресс-прогоне 1 запрос завершился ошибкой `connectex: Only one usage of each socket address ... is normally permitted`. Сервер не упал: у клиента (Windows) закончились свободные локальные порты. Встроенный сервер Flask закрывает соединение после каждого ответа (HTTP/1.0 без keep-alive), поэтому за 10 с открылось и закрылось ~11,5 тыс. TCP-соединений, а закрытые порты какое-то время остаются в состоянии TIME_WAIT. Первым при перегрузке сдаёт сетевой уровень, а не логика приложения.

## 6. Выводы

1. Для 10 и 50 одновременных пользователей с реалистичными паузами стенд выполняет все цели: p(95) ≤ 50 мс при пороге 300 мс, ошибок нет.
2. Предел встроенного сервера на этом компьютере — около 1150 запросов в секунду; дальше появляются ошибки соединений.
3. Для повышения устойчивости стоит запускать приложение на сервере с поддержкой keep-alive и несколькими потоками или процессами (waitress, gunicorn за nginx). Встроенный сервер Flask предназначен только для разработки.
4. Ограничение эксперимента: k6 и стенд работали на одном компьютере и делили процессор, поэтому абсолютные цифры ориентировочные.
